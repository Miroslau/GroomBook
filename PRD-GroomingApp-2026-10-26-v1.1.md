# PRD: Grooming App

**Версия:** 1.1 (черновик для обратной связи)  
**Дата:** 26.10.2026  
**Платформа:** Android (React Native + Expo SDK 58, TypeScript)  
**Данные:** Cloud Firestore (коллекции) с локальным офлайн-кэшем, вход через Google  
**Распространение:** личный APK, без публикации в Google Play

---

## Что изменилось по сравнению с версией 1.0

| Что | Было (v1.0) | Стало (v1.1) | Почему |
|---|---|---|---|
| Навигация | `expo-router` | React Navigation | Решение разработчика |
| Хранение данных | Локальная SQLite | Cloud Firestore (коллекции) + офлайн-кэш на телефоне | Нужна синхронизация и работа без интернета |
| Аккаунты | Не нужны | Вход через Google (Firebase Auth) | Firestore должен знать, чьи это данные |
| Резервная копия | Основной способ защиты данных | Дополнительная функция (экспорт в JSON) | Данные теперь в облаке |
| Подсказки при вводе | SQL-запросы по записям | Отдельная коллекция подсказок со счётчиками | В Firestore нет поиска «по началу строки с подсчётом частоты» |
| Уникальность слота | `UNIQUE (date, slot_hour)` в SQLite | Идентификатор документа = `дата_час` | В Firestore нет ограничений уникальности |
| Напоминания | Хранение идентификаторов уведомлений в записи | Полное пересоздание расписания (отменить всё и запланировать заново) | Записи могут меняться с другого устройства |
| Затраты | Нулевые | Нулевые (бесплатный план Firebase Spark) | Квот хватает с большим запасом |

## 1. Обзор приложения и цели

### 1.1 Описание
Grooming App — мобильное приложение для Android, которое заменяет бумажную тетрадь записи клиентов груммера («Книга для записи животных DEWAL PRO GROOMING», формат A4). В тетради есть таблица с колонками: время, клиент, порода/кличка животного, услуга. Но нет календаря: нельзя быстро увидеть, на какие дни и недели есть записи.

Приложение сохраняет привычную логику «страницы дня как в блокноте» и добавляет то, чего не хватает: календарь, быстрый перенос записей, подсказки при вводе, напоминания, работу без интернета и синхронизацию данных через облако.

### 1.2 Проблема
- В бумажной тетради нельзя быстро оценить загрузку по неделям и месяцам.
- Перенос записи на другой день означает зачёркивание и переписывание.
- Клиентов, породы и услуги приходится каждый раз писать вручную.
- Тетрадь легко потерять, а записи нельзя восстановить.

### 1.3 Цели первой версии (MVP)
1. Войти через Google один раз и сразу увидеть страницу текущего дня с таблицей записей.
2. Быстро перейти на любой другой день через полоску недели и месячный календарь.
3. Создавать, изменять, удалять и переносить записи за несколько нажатий.
4. Получать напоминания (утренний список и напоминание перед каждой записью).
5. Работать без интернета: записи доступны и редактируются офлайн, а при появлении сети автоматически синхронизируются.
6. Не потерять данные: записи хранятся в облаке и доступны после переустановки приложения или на другом устройстве.

### 1.4 Вне рамок MVP (non-goals)
Несколько мастеров и общий доступ к одним данным, телефоны/цены/заметки клиентов, напоминания клиентам по SMS, публикация в Google Play, iOS, тёмная тема, вход другими способами (email, Apple).

## 2. Целевая аудитория

- **Основной пользователь:** один груммер (индивидуальный мастер), ведущий свои записи самостоятельно.
- **Устройства:** Android-телефон; допускается использование на нескольких своих устройствах под одним Google-аккаунтом.
- **Уровень технической подготовки:** обычный пользователь смартфона. Интерфейс должен быть понятен без инструкции.
- **Язык интерфейса:** русский.
- **Часовой пояс:** локальный часовой пояс устройства (Europe/Minsk, UTC+03:00).
- **Требование к первому запуску:** при первом входе нужен интернет; дальше приложение работает офлайн.

| Параметр | Значение |

### Функция F0. Вход через Google

**Описание.** При первом запуске показывается экран входа с кнопкой «Войти через Google». После успешного входа открывается страница текущего дня. Сессия сохраняется между запусками.

**Acceptance criteria:**
- Экран входа показывается только если пользователь не авторизован.
- Кнопка «Войти через Google» открывает системный выбор Google-аккаунта; после выбора пользователь попадает на главный экран.
- Сессия сохраняется после перезапуска приложения и работает без интернета (повторный вход не требуется).
- При первом входе без интернета показывается сообщение «Для первого входа нужен интернет».
- Ошибки входа (отмена, нет сети, ошибка сервиса) показываются понятным сообщением, без сбоя приложения.
- В настройках отображаются имя/почта аккаунта и кнопка «Выйти» с подтверждением. После выхода запланированные уведомления отменяются и показывается экран входа.
- Данные каждого пользователя изолированы: пользователь видит только свои записи.

**Technical Considerations:**
- Firebase Authentication с провайдером Google (`@react-native-firebase/auth`).
- Для получения Google-токена нужна библиотека входа: `@react-native-google-signin/google-signin` или `react-native-nitro-google-signin` (Expo рекомендует обе; у первой часть возможностей Credential Manager платная, перед выбором проверить лицензию). Документация: https://docs.expo.dev/guides/google-authentication/
- Алгоритм: получить ID-токен Google → создать Firebase-учётные данные (`GoogleAuthProvider.credential`) → `signInWithCredential`.
- Настройка: добавить в Firebase-проект Android-приложение с нужным `package name`, зарегистрировать **SHA-1 отпечаток** ключа подписи (и для development build, и для итогового APK, если подпись отличается), включить провайдер Google в Authentication, скачать `google-services.json`.
- Типичная ошибка настройки: код `DEVELOPER_ERROR` — означает несоответствие SHA-1/пакета или `webClientId`.
- Работает только в development build, не в Expo Go.

### Функция F1. Экран дня («страница блокнота») — главный экран

**Описание.** После входа приложение открывает страницу текущего дня. Страница выглядит как таблица из строк-слотов, по одной на каждый час рабочего дня.

**Структура строки слота:**
- время слота (например, `10:00`);
- клиент;
- порода/кличка животного;
- услуга.

Пустая строка отображается как свободная; нажатие на неё открывает создание записи на этот слот.

**Acceptance criteria:**
- При запуске отображается сегодняшняя дата и 10 строк слотов (при настройках по умолчанию).
- Заголовок экрана показывает дату и день недели (например, «Понедельник, 26 октября 2026»).
- Занятые строки показывают три поля записи; свободные визуально отличаются (пустые, с подсказкой «Добавить запись»).
- Если в дне есть записи вне текущего рабочего диапазона (после смены настроек), они всё равно отображаются в виде дополнительных строк.
- Экран открывается и показывает ранее загруженные записи без интернета.
- Изменения, сделанные с другого устройства, появляются на экране автоматически (при наличии сети).

**Technical Considerations:**
- Слоты строятся из настроек `workStartHour` / `workEndHour`, затем объединяются с записями дня (запись по ключу `slotHour`).
- Данные дня: слушатель `onSnapshot` на запрос по полю `date` (или чтение документов по известным идентификаторам `date_hour`).
- Для списка использовать `FlatList`.

### Функция F2. Навигация по датам: полоска недели

**Описание.** Над таблицей дня — горизонтальная полоска недели Пн–Вс. Выбранный день выделен, сегодняшний помечен отдельно. Свайп влево/вправо листает недели.

**Acceptance criteria:**
- Полоска показывает 7 дней текущей выбранной недели (Пн–Вс) с числом месяца.
- Нажатие на день переключает страницу дня.
- Свайп по полоске переключает неделю на предыдущую/следующую.
- Под каждым днём отображается число записей, если оно больше нуля.
- Кнопка «Сегодня» возвращает на текущий день и неделю.

**Technical Considerations:**
- Один запрос к коллекции `appointments` с диапазоном `date >= понедельник` и `date <= воскресенье`; число записей по дням считается на клиенте (группировка по `date`).
- Загружать данные недели одним слушателем, а не 7 отдельными.

### Функция F3. Месячный календарь

**Описание.** По кнопке (иконка календаря в шапке) открывается календарь на месяц. Дни с записями помечены числом записей. Нажатие на день открывает его страницу.

**Acceptance criteria:**
- Отображается сетка месяца с неделями, начинающимися с понедельника.
- На днях с записями показано их число; на днях без записей пометки нет.
- Сегодняшний день и выбранный день визуально выделены.
- Переключение месяцев кнопками «назад/вперёд» и свайпом.
- Нажатие на день закрывает календарь и открывает страницу этого дня.
- Работает офлайн (на основе локального кэша).

**Technical Considerations:**
- Один запрос с диапазоном дат на месяц (`date` от `YYYY-MM-01` до `YYYY-MM-31`), подсчёт на клиенте. Это не более ~310 документов в месяц (31 день × 10 слотов), нагрузка на бесплатные квоты минимальна.
- Допустимы два подхода: готовая библиотека (например, `react-native-calendars`, перед использованием проверить совместимость с SDK 58 и New Architecture) или собственная сетка месяца на `View` с датами через `date-fns`. Решение принять на этапе M3; предпочтительно простая собственная сетка, если библиотека создаёт проблемы.

### Функция F4. Создание записи

**Описание.** Нажатие на свободный слот открывает форму (модальный экран) с полями.

**Поля формы:**
- `clientName` — клиент (обязательное, текст);
- `pet` — порода/кличка животного (необязательное, текст);
- `service` — услуга (необязательное, текст);
- дата и время слота подставляются автоматически и показываются только для чтения (меняются через «Перенести»).

**Acceptance criteria:**
- Нельзя сохранить запись без `clientName` (показывается сообщение об ошибке у поля).
- После сохранения запись сразу видна в строке слота (даже без интернета).
- Нельзя создать вторую запись в занятый слот (проверка по локальным данным до сохранения).
- Все три текстовых поля поддерживают подсказки (см. F8).
- Максимальная длина каждого поля — 100 символов.
- Лишние пробелы в начале и конце значений убираются при сохранении.

**Technical Considerations:**
- Идентификатор документа: `{date}_{slotHour}` (например, `2026-10-26_10`). Это гарантирует, что в один слот не попадёт два документа.
- Запись выполняется через `set` (работает офлайн, ставится в очередь и отправляется при появлении сети).
- Поля времени создания/изменения — серверные метки времени (`serverTimestamp`).

### Функция F5. Изменение записи

**Acceptance criteria:**
- Нажатие на занятую строку открывает карточку записи с возможностью редактирования полей `clientName`, `pet`, `service`.
- Сохранение обновляет строку на странице дня.
- Для изменения даты/времени используется «Перенести» (F7), а не редактирование полей.

### Функция F6. Удаление записи

**Acceptance criteria:**
- В карточке записи есть действие «Удалить».
- Перед удалением показывается подтверждение («Удалить запись?»).
- После подтверждения запись исчезает, слот становится свободным, счётчик в календаре уменьшается, расписание напоминаний пересоздаётся.
- Удаление работает офлайн и синхронизируется при появлении сети.

### Функция F7. Перенос записи

**Описание.** Запись можно перенести на другой день и/или другое время.

**Acceptance criteria:**
- В карточке записи есть действие «Перенести».
- Пользователь выбирает новую дату (через календарь) и слот времени.
- Если выбранный слот занят, перенос отклоняется с сообщением «Этот слот уже занят». Автоматической замены нет.
- После переноса запись видна на новой дате/времени и исчезает со старой; расписание напоминаний пересоздаётся.
- Данные записи (клиент, питомец, услуга) сохраняются без изменений.
- Перенос работает офлайн.

**Technical Considerations:**
- Так как идентификатор содержит дату и час, перенос — это **удаление старого документа и создание нового** в одной пакетной записи (`writeBatch`), а не обновление полей.
- **Не использовать транзакции**: в Firestore они требуют подключения к сети и не работают офлайн. Пакетные записи (batch) офлайн работают.

**Pseudocode:**
```
moveAppointment(oldId, newDate, newSlotHour):
  newId = newDate + "_" + newSlotHour
  if localCache has document newId:
    return Error("slot_occupied")
  data = read document oldId
  batch = new writeBatch
  batch.delete(oldId)
  batch.set(newId, data with date = newDate, slotHour = newSlotHour, updatedAt = serverTimestamp)
  batch.commit()
  rescheduleAllNotifications()
```

### Функция F8. Подсказки при вводе (autocomplete)

**Описание.** Приложение запоминает ранее введённые значения и предлагает их при вводе: клиенты, породы/клички, услуги.

**Acceptance criteria:**
- При вводе от 1 символа в любое из трёх полей показывается до 5 подходящих вариантов.
- Подсказки берутся из ранее сохранённых записей; сортировка: сначала по частоте использования, затем по давности.
- Нажатие на подсказку подставляет значение в поле.
- Сопоставление без учёта регистра, по началу слова.
- Подсказки работают офлайн.
- Отдельные справочники в интерфейсе не нужны; новые значения запоминаются автоматически при сохранении записи.

**Technical Considerations:**
- Отдельная коллекция `suggestions` (см. раздел 5): документ на каждое уникальное значение с полями `type`, `value`, `valueLower`, `useCount`, `lastUsedAt`.
- При сохранении записи для каждого непустого поля выполнить upsert документа подсказки с `useCount = increment(1)` и `lastUsedAt = serverTimestamp`.
- Запрос подсказок: `type == X` и `valueLower` в диапазоне от префикса до префикс + ``, сортировка по `valueLower`, лимит ~20; затем на клиенте отсортировать по `useCount` и `lastUsedAt` и показать 5.
- Для запроса нужен составной индекс (`type`, `valueLower`); консоль Firebase подскажет создать его при первой ошибке.
- Запрос с лёгким debounce (≈150 мс), чтобы не блокировать ввод.
- Счётчики при удалении записей не уменьшаются (допустимое упрощение).

### Функция F9. Уведомления-напоминания

**Описание.** Два типа локальных уведомлений, работающих без интернета и планируемых на самом устройстве:
1. **Утренний список:** в заданное время (по умолчанию 08:30) приходит уведомление со списком записей на сегодня.
2. **Напоминание перед записью:** за 60 минут (по умолчанию) до начала слота.

**Acceptance criteria:**
- Оба типа можно включать и выключать независимо в настройках.
- Время утреннего уведомления настраивается; интервал «за сколько напоминать» настраивается (например, 30/60/120 минут).
- Утреннее уведомление содержит число записей и краткий список (время, клиент). Если записей на день нет, уведомление не отправляется.
- Напоминание перед записью содержит время, клиента, питомца и услугу.
- Расписание пересоздаётся при запуске приложения, при любом изменении записей (в том числе пришедшем с другого устройства), при смене настроек и при входе/выходе.
- Напоминания не создаются для прошедшего времени.
- При первом запуске приложение запрашивает разрешение на уведомления (Android 13+: `POST_NOTIFICATIONS`). Если разрешение отклонено, в настройках показывается подсказка, как его включить.
- Запланированные уведомления сохраняются после перезагрузки телефона.

**Technical Considerations:**
- Библиотека: `expo-notifications` (локальные уведомления работают без сети, документация: https://docs.expo.dev/versions/latest/sdk/notifications/).
- Подход «отменить всё и запланировать заново»: на каждое изменение вызвать отмену всех запланированных уведомлений и запланировать утренние списки и напоминания на ближайшие 14 дней. Идентификаторы уведомлений в данных не хранятся. Объём: не более ~150 уведомлений, это допустимо для Android.
- Утреннее уведомление имеет динамическое содержимое, поэтому повторяющийся триггер не подходит: планируются отдельные уведомления на каждую дату.
- Создать Android-канал уведомлений (например, `appointments`) с высокой важностью.
- Известный риск: если запись изменена на другом устройстве, а это приложение не запускалось, расписание останется устаревшим до следующего открытия (решение через push-уведомления вынесено в будущие расширения).
- Известный риск: на Android плановые уведомления могут срабатывать с задержкой при экономии батареи. Проверить поведение на реальном устройстве; при необходимости подсказать отключить оптимизацию батареи и рассмотреть разрешение на точные будильники.

### Функция F10. Настройки

**Acceptance criteria:**
- Рабочий день: время начала и конца (целые часы, начало < конца, диапазон 00:00–24:00).
- Утренний список: вкл/выкл и время.
- Напоминание перед записью: вкл/выкл и интервал.
- Аккаунт: имя/почта, кнопка «Выйти» (см. F0).
- Дополнительно: «Экспорт записей в файл» (см. F12).
- Изменение рабочих часов не удаляет и не скрывает существующие записи.
- Настройки хранятся в облаке и применяются на всех устройствах пользователя.

### Функция F11. Синхронизация и работа без интернета

**Описание.** Все операции (просмотр, создание, изменение, удаление, перенос) работают без интернета. Изменения накапливаются локально и автоматически отправляются в облако при появлении сети.

**Acceptance criteria:**
- Без интернета приложение открывается, показывает ранее загруженные данные и позволяет вносить изменения.
- После восстановления сети изменения отправляются автоматически, без действий пользователя.
- В шапке экрана отображается индикатор состояния: «Синхронизировано», «Ожидает синхронизации» (есть неотправленные изменения) или «Нет сети».
- Изменения, сделанные на другом устройстве, подтягиваются автоматически при наличии сети.
- При одновременном редактировании одной записи на двух устройствах побеждает последнее по времени изменение; приложение не должно падать.
- После переустановки приложения и входа тем же Google-аккаунтом все записи возвращаются.

**Technical Considerations:**
- Использовать `@react-native-firebase/firestore`, а не JS SDK `firebase`: JS SDK не поддерживает офлайн-кэш в React Native (нет IndexedDB, откат на кэш в памяти). Нативная библиотека использует собственный кэш на устройстве.
- Подтвердить на этапе M0 тестом в режиме «В самолёте»: запись и чтение офлайн, перезапуск приложения офлайн, синхронизация после возврата сети.
- Индикатор состояния строится на метаданных снимков (`metadata.hasPendingWrites`, `metadata.fromCache`) и состоянии сети.
- Размер кэша по умолчанию достаточен; настраивать не требуется.

### Функция F12. Экспорт записей в файл (дополнительно, can-have)

**Описание.** Запасной способ получить свои данные: выгрузка всех записей в JSON-файл.

**Acceptance criteria:**
- Кнопка «Экспорт записей» формирует файл `grooming-export-YYYY-MM-DD.json` и открывает системное меню «Поделиться».
- Файл содержит все записи и настройки (формат см. раздел 5.4).
- Импорт из файла в MVP не входит.

**Technical Considerations:**
- Библиотеки: `expo-file-system`, `expo-sharing`.
- Реализуется последним и может быть перенесено в следующую версию, если время ограничено.

## 5. Концептуальная модель данных

Все данные хранятся в Firestore внутри пространства пользователя: `users/{uid}/...`, где `uid` — идентификатор пользователя Firebase Auth.

### 5.1 Коллекция `users/{uid}/appointments`

Идентификатор документа: `{date}_{slotHour}`, например `2026-10-26_10`.

| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| `date` | string | `YYYY-MM-DD` | Локальная дата визита |
| `slotHour` | number | целое, 0–23 | Час начала слота |
| `clientName` | string | обязательное, ≤ 100 | Клиент |
| `pet` | string | ≤ 100 | Порода/кличка |
| `service` | string | ≤ 100 | Услуга |
| `createdAt` | timestamp | серверное время | Дата создания |
| `updatedAt` | timestamp | серверное время | Дата изменения |

**Ограничения и индексы:**
- Уникальность слота обеспечивается идентификатором документа.
- Запросы по диапазону дат (`date`) используют встроенный индекс по одному полю, составной индекс не нужен.

### 5.2 Документ `users/{uid}/settings/main`

| Поле | Тип | По умолчанию |
|---|---|---|
| `workStartHour` | number | 9 |
| `workEndHour` | number | 19 |
| `morningDigestEnabled` | boolean | true |
| `morningDigestTime` | string `HH:mm` | `08:30` |
| `reminderEnabled` | boolean | true |
| `reminderOffsetMinutes` | number | 60 |

### 5.3 Коллекция `users/{uid}/suggestions`

Идентификатор документа: `{type}_{valueLower}` (например, `client_иванова`).

| Поле | Тип | Описание |
|---|---|---|
| `type` | string | `client`, `pet` или `service` |
| `value` | string | Значение как введено (с исходным регистром) |
| `valueLower` | string | Значение в нижнем регистре для поиска по началу |
| `useCount` | number | Сколько раз использовалось |
| `lastUsedAt` | timestamp | Когда использовалось в последний раз |

Для запроса подсказок нужен составной индекс: `type` (по возрастанию) + `valueLower` (по возрастанию).

### 5.4 Формат файла экспорта (F12)
```
{
  "schemaVersion": 1,
  "exportedAt": "ISO 8601",
  "settings": { ... поля из settings/main ... },
  "appointments": [ { date, slotHour, clientName, pet, service }, ... ]
}
```

### 5.5 Правила безопасности Firestore (требование)
Описание правил (формулировка, а не готовый код):
- Любой доступ (чтение и запись) к документам `users/{uid}/...` разрешён только если пользователь авторизован и `request.auth.uid` равен `uid` из пути.
- Любой другой путь закрыт для всех.
- Дополнительно (желательно): проверка длины текстовых полей ≤ 100 символов и допустимого значения `type` в подсказках.
- Не оставлять тестовый режим «открыто всем» после начала разработки.

Документация: https://firebase.google.com/docs/firestore/security/get-started

## 7. Соображения по безопасности и приватности

- **Авторизация:** вход только через Google (Firebase Auth); без собственных паролей.
- **Изоляция данных:** правила Firestore разрешают доступ только владельцу (см. 5.5). Это главный механизм защиты: данные доступны только после входа и только своему пользователю.
- **Ключи в `google-services.json`:** это не секреты в обычном смысле (они определяют проект, а не дают доступ); защита обеспечивается правилами безопасности, а не скрытием файла.
- **Персональные данные:** имена клиентов и данные питомцев хранятся в облаке Google (Firebase). Телефоны, адреса и платёжные данные не хранятся. Пользователь должен понимать, что данные клиентов хранятся в облачном сервисе.
- **Локальный кэш** хранится в приватной области приложения на устройстве.
- **Разрешения Android:** уведомления (`POST_NOTIFICATIONS`), доступ в интернет, запуск после перезагрузки для восстановления уведомлений. Лишних разрешений (контакты, местоположение, камера) не запрашивать.
- **Экспорт в файл** содержит имена клиентов; перед отправкой предупредить пользователя.
- Защита экрана ПИН-кодом/биометрией в MVP не нужна (вынесено в будущие расширения).

## 9. Потенциальные проблемы и способы их решения

| Проблема | Риск | Решение |
|---|---|---|
| Ошибка входа `DEVELOPER_ERROR` / неверный SHA-1 | Вход через Google не работает в dev build или в релизном APK | Зарегистрировать SHA-1 каждого используемого ключа подписи в Firebase; проверить `package name` и `webClientId` |
| Совместимость Firebase, Google Sign-In и React Navigation 8 с SDK 58 / RN 0.88 | Блокировка на старте | Проверить на M0; зафиксировать версии; запасной план для навигации — React Navigation 7 |
| Нет IndexedDB в React Native | JS SDK Firebase не хранит данные офлайн | Использовать `@react-native-firebase/firestore` (нативный) вместо `firebase` JS SDK |
| Транзакции Firestore не работают офлайн | Перенос записи может не сработать без сети | Использовать пакетные записи (`writeBatch`) вместо транзакций |
| Конфликты при одновременном изменении на двух устройствах | Одно из изменений теряется | Политика «побеждает последнее изменение»; клиентская проверка занятости слота; сценарий допустим для одного пользователя |
| Первый вход без интернета невозможен | Пользователь не может начать работу офлайн | Понятное сообщение; требование к первому запуску |
| Устаревшее расписание уведомлений после изменений с другого устройства | Напоминание придёт по старым данным | Пересоздавать расписание при каждом запуске; push-обновление — в будущие расширения |
| Задержки плановых уведомлений на Android | Напоминание придёт позже | Проверка на реальном устройстве; подсказка отключить оптимизацию батареи; при необходимости точные будильники |
| Выход за бесплатные квоты Firebase | Блокировка операций | Использовать один слушатель на неделю/месяц, а не множество мелких; следить за использованием в консоли Firebase |
| Открытые правила безопасности | Данные доступны посторонним | Настроить правила до начала работы с реальными данными (см. 5.5) |
| Хранение данных клиентов в облаке | Вопросы приватности | Хранить минимум данных (без телефонов и адресов); пояснить в приложении, где хранятся данные |
| Дубли написания в подсказках («Иванова»/«иванова») | Грязные подсказки | Нормализация (`valueLower`), удаление лишних пробелов |
| R8 в релизных сборках | Релизный APK ведёт себя иначе, чем dev build | Тестировать релизную сборку на M7 |
| Часовые пояса и переход на летнее время | Неверное время напоминаний | Хранить дату и час как локальные значения; вычислять время уведомления в локальной зоне устройства |

## 10. Возможности будущего расширения
